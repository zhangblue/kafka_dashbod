# Kafka 凭据明文存储设计

## 目标

移除 `KAFKA_DASHBOARD_MASTER_KEY` 配置要求。应用在未设置任何主密钥的情况下可以启动、保存 Kafka 集群配置并建立只读监控连接。

用户明确接受 Kafka 敏感配置以明文形式保存在 SQLite 中，并接受新版本不兼容已有加密数据库。升级时必须删除旧数据库并重新配置集群。

## 数据与安全边界

以下字段直接序列化并保存到 SQLite，不再经过应用层加密：

- SASL 密码；
- TLS CA PEM；
- TLS 客户端证书 PEM；
- TLS 客户端私钥 PEM；
- TLS 客户端私钥口令。

取消静态加密不改变其他安全边界：

- HTTP API 只返回“是否已配置”的标志，不回显敏感值；
- 日志、错误响应、Request ID 关联日志和测试产物不得包含凭据；
- 编辑时继续支持保留、替换和显式清除敏感字段；
- 草稿连接测试继续复用已保存凭据，但不得将凭据写入响应或日志；
- 发行启动器继续使用 `umask 077` 创建私有数据目录。

README 必须明确提示：任何能够读取 SQLite 文件的人都可以读取 Kafka 凭据，应使用操作系统文件权限、磁盘加密和受控备份保护数据目录。

## 后端设计

删除启动配置中的主密钥读取和校验，删除 `SecretCipher` 以及不再使用的 AES-GCM、Base64 加解密依赖。应用状态和集群仓库不再接收密码器。

集群仓库将凭据结构序列化为 JSON 字节保存，并在读取时直接反序列化。数据库字段使用反映明文语义的名称，避免继续使用 `encrypted` 等误导性命名。

初始迁移直接修改为新结构，不提供旧密文识别、解密或自动迁移。由于既有迁移校验和及字段语义发生变化，旧数据库属于不支持的输入；启动错误和文档应明确要求删除旧数据库后重新配置，而不是尝试将密文当作明文读取。

## 启动与发行行为

源码运行和发行目录的 `start.sh` 均不再要求 `KAFKA_DASHBOARD_MASTER_KEY`。示例配置、发行说明和 README 删除该变量及生成命令。

`start.sh` 保持现有平台选择逻辑：

- `Darwin/arm64` 运行 `bin/kafka-dashboard-darwin-arm64`；
- `Linux/x86_64` 运行 `bin/kafka-dashboard-linux-amd64`；
- 其他平台明确报错退出。

启动器一次只运行当前平台对应的二进制。

## 兼容性与升级

本次变更明确不兼容已使用 `KAFKA_DASHBOARD_MASTER_KEY` 创建的数据库。升级步骤为：

1. 停止旧版本；
2. 如需留档，在安全位置备份旧数据库及旧主密钥；
3. 删除发行目录中的旧 `data/kafka-dashboard.db` 及 SQLite sidecar 文件；
4. 启动新版本；
5. 在页面中重新添加 Kafka 集群和 Lag 规则。

应用不实现隐式数据删除。检测到旧迁移或旧结构时应拒绝使用并提示人工删除，避免静默丢失配置。

## 错误处理

- 不再出现“主密钥缺失”或“主密钥格式错误”错误；
- 明文凭据 JSON 无法解析时，返回脱敏的配置存储错误，不输出原始数据；
- 旧数据库或迁移校验不匹配时，错误信息指出数据库版本不兼容以及重新创建要求；
- Kafka 原生错误仍映射为既有安全错误码，不得包含密码、PEM、broker 凭据或数据库内容。

## 测试与验收

实现必须按测试驱动方式覆盖：

- 未设置 `KAFKA_DASHBOARD_MASTER_KEY` 时后端和发行启动器正常启动；
- 新增、读取、编辑、保留、替换和清除五类敏感字段；
- SQLite 中保存的是预期明文凭据，API 和日志仍不回显；
- 旧数据库结构或迁移不兼容时拒绝启动并给出安全提示；
- `start.sh` 在 macOS ARM 和 Linux x86_64 只选择对应二进制；
- Rust、前端、E2E、发布脚本和双平台发行包验证全部通过；
- README、`AGENTS.md`、发行说明和示例配置不再要求主密钥，并明确明文存储风险与升级步骤。

## 非目标

- 不实现旧加密数据库的自动迁移；
- 不保留可选的 `KAFKA_DASHBOARD_MASTER_KEY` 兼容模式；
- 不引入操作系统钥匙串、外部 Secret Manager 或额外认证系统；
- 不改变 Kafka 只读采集、会话租约、Lag 规则和一小时内存历史行为。
